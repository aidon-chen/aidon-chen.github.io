这篇不铺垫，直接写踩过的坑。每个坑都是实际撞上、改过代码的，不是从文档里抄的注意事项。

## 权限：前端直写看起来很美

云开发的数据库权限规则有四种模式，配起来很简单。问题是它只能回答「这条记录是不是你创建的」，回答不了「你是不是主任」「这条任务能不能改」。

举个例子。任务由主任创建，指派给成员。如果用「仅创建者可读写」，成员读不到这条任务，因为记录是主任创建的；如果用「所有用户可读」，全中心的人都能看到别人的任务；如果放开写权限，任何人都能把任务状态改成已完成。规则里没有「被指派人可以改状态但不能改标题」这一档。

所以这个项目最后所有写操作都放在云函数里。云函数用的是管理员权限，不受数据库权限规则限制，判断逻辑全在代码里。前端只调 `wx.cloud.callFunction`，不直接碰 `db.collection`。

但有一个地方没守规矩。`app.js` 里刷新未读红点时，直接查了数据库：

```js
const db = wx.cloud.database();
const res = await db.collection('notifications')
  .where({ userId: userInfo._id, isRead: false })
  .count();
```

同一件事，「我的」页用的是云函数 `getNotifications`，`app.js` 用的是前端直查。两处实现不一样，连红点挂的 tab 都不一样：`app.js` 挂在 index 0，`utils/notification.js` 挂在 index 3。只要其中一处出问题，用户看到的现象就是「有时有红点，有时没有」。

更麻烦的是，前端直查如果权限收紧，会静默失败。`app.js` 里包了 `try/catch`，失败不报错、不影响主流程，结果就是红点永远不亮，你还不容易发现。现在「我的」页和 tab 红点主要走云函数 `getNotifications`，`app.js` 里那段直查还留着，属于没清干净的历史代码。

结论：云函数能干的活不要让前端干。前端直读只适合公开的只读数据，比如机位列表、新闻缓存。

## 订阅消息：模板 ID 是占位符

第一版通知用的是微信订阅消息。`sendNotification` 里配置了三个模板 ID：

```js
const TEMPLATE_IDS = {
  task_assigned: 'your-template-id-task-assigned',
  task_reminder: 'your-template-id-task-reminder',
  task_cancelled: 'your-template-id-task-cancelled'
};
```

这三个值都是占位符。代码能跑，任务能创建，日志也不报错，因为发送失败被 `try/catch` 包住，只记了一条「未发送」。上线前测试才发现，没有任何人收到过通知。

就算把真实模板 ID 填上，订阅消息还有两层限制。

第一，用户必须授权。调 `wx.requestSubscribeMessage` 弹一次窗，用户点了允许，才能发一条对应类型的消息。没授权的用户，代码只能静默跳过。

第二，一次性订阅通常只能发一次。任务提醒这种需要反复触达的场景，用户每次都得重新授权，体验很差。长期订阅只对特定行业开放，普通小程序申请不下来。

模板字段也是固定的。申请时选了哪几个关键词，代码里就只能填哪几个，多一个少一个都不行。想改文案要重新申请模板，审核还要等。

最后这个项目改成了小程序内通知：`sendNotification` 往 `notifications` 集合写记录，前端在「我的」页做消息中心，tab 上加红点。用户不开小程序就收不到，这是它的缺点；但消息可查、可回溯，不依赖授权，对内部工具来说更合适。

改完之后，`sendNotification` 的核心就是逐条写记录：

```js
const records = targets.map((userId) => ({
  userId,
  taskId: taskId || '',
  type,
  content: text,
  isRead: false,
  createdAt: db.serverDate()
}));

for (const rec of records) {
  await notificationsCollection.add({ data: rec });
}
```

单条失败不影响其他条。这个循环是串行的，人数多的时候会慢，但四十个人以内还能接受。

## 定时器：提前两小时，实际不一定

`scheduleNotify` 的配置是：

```json
{
  "triggers": [
    {
      "name": "taskScanner",
      "type": "timer",
      "config": "0 */30 * * * * *"
    }
  ]
}
```

云开发的定时触发器是七段 cron：秒、分、时、日、月、周、年。这个表达式表示每 30 分钟触发一次。不是「任务开始前两小时整点触发」，而是「每半小时扫一遍，扫到开始时间在 [now-5min, now+2h] 之间的任务就提醒」。所以实际提前量在 1.5 到 2 小时之间浮动，取决于任务开始时间和触发点的相对位置。

这个偏差我能接受，但写文档的时候要写清楚，不然别人会以为是精确的两小时。

定时器还有几个和普通云函数不一样的地方。

第一，触发时没有用户上下文，`cloud.getWXContext().OPENID` 是空的。所以 `scheduleNotify` 不能按「当前用户」查数据，只能直接扫集合。

第二，提醒只扫 `status: 'confirmed'` 的任务。如果成员一直没点「开始」，任务还是 `confirmed`，会收到提醒；如果他提前点了「开始」，状态变成 `in_progress`，反而不在扫描范围里。这个逻辑当时没想周全，后来用下来影响不大，就先留着了。

第三，提醒文案有个 bug。代码里是这样拼的：

```js
const content =
  type === NOTIFY_TYPES.reminder
    ? `任务即将开始：${title}（${formatTime(null)}）`
    : `任务已自动完成：${title}`;
```

`formatTime(null)` 永远返回「即将开始」，所以通知内容变成「任务即将开始：迎新晚会拍摄（即将开始）」。括号里本来想放任务时间，结果传了 `null`。这个 bug 是看消息中心截图才发现的，改起来一行的事，但没人提醒的话会一直躺在那里。

第四，防重靠 `notifiedAt`。扫到任务后，先给每个成员写通知，再给任务打标记。如果函数在写通知的过程中超时，标记没打上，下一轮会重复发。正确做法是先把标记写上、再发通知，或者给每条通知加一个唯一键做幂等。

第五，查询用了 `limit(100)`，写通知是串行 `await`。任务多、成员多的时候，一轮可能跑不完 100 条，或者直接超时。四十个人的规模暂时够用，人数再涨就得改批量写。

## 本地和线上不一样

云函数在开发者工具里可以本地调试，但本地和线上有几个差异，排查问题时要注意。

`cloud.DYNAMIC_CURRENT_ENV` 在本地会指向你当前选的环境，线上指向部署时所在的环境。如果你本地连的是测试环境，线上跑的是生产环境，同一段代码查到的数据可能完全不同。

定时器触发时没有 OPENID，本地手动调用时也没有。调试 `scheduleNotify` 不能靠「当前用户」构造数据，要直接往集合里塞测试任务。

测试开关分散在 13 个文件里：前端 `config/test.js` 一个，云函数 `testConfig.js` 十二个。只要有一个忘了关，测试逻辑就可能跟着发布版上线。项目里写了 `switch-mode.js` 一键切换，但脚本本身也出过问题：最初的正则改了注释、没改真实字段，后来改成取最后一个匹配才对。

部署脚本还有一个跨平台问题。`switch-mode.js` 里把开发者工具 CLI 的路径写死成了：

```js
const CLI_BAT = 'F:/toolapp2/微信web开发者工具/cli.bat';
```

在 Windows 上没问题，换到 Mac 上直接找不到命令。后来 `deploy-functions.js` 留了 `TD_DEPLOY_CMD` 环境变量，可以把命令模板换掉，但 `switch-mode.js` 这块一直没改成跨平台。一个人开发的时候能忍，多人协作就得先修。

还有一个和事务有关的坑。`verifyKey` 要同时改两个地方：把密钥标记为已使用，把用户角色升上去。代码里注释写着「小程序云开发基础版不支持事务，使用两步更新」。两步更新意味着中间可能失败：密钥已经标记成已使用，角色却没升上去，用户再试一次会提示「密钥已被使用」，只能人工去控制台改。这个概率不高，但真发生的时候很难解释。

## 什么规模适合云开发

四十个人、内部使用、没有专职运维，云开发很合适。免费额度够用，登录态白送，改一个云函数就能上线，不用管服务器。

不适合的情况也很明确：要做 Web 管理端，登录态打不通；要跑复杂报表或长任务，云函数超时和定时器粒度都不够；要接外部系统，网络和域名限制会让人难受。

我的体会是，云开发不是「不用管后端」，而是把运维换成了另一套边界。你要管的是云函数的超时、数据库的索引、权限规则的例外、定时器的时间窗。这些和管服务器不是一回事，但同样需要心里有数。
