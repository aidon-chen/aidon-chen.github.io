湖里 Lakes：上线前搭的四层测试

发表于2026-10-01|更新于2026-11-14|微信小程序点餐系统
|总字数:2.4k|阅读时长:7分钟|浏览量:

测试这件事，最怕的是脚本全绿，但心里知道它不能开业。

湖里 Lakes 做到九月底，功能基本能演示了：扫码能点单，收银台能结账，会员能领券，商城能下自提单。但我很清楚，这些只能证明「演示那天不翻车」，离「店里真敢用」还差得远。于是花了一周搭测试，最后落成四层。

四层不是为了好看。一层管一件事，出问题的时候能立刻知道该去哪一层查：是接口挂了，是页面点不通，是需求没做到，还是并发扛不住。

L1：接口冒烟，先确认服务活着

第一层最快，也最基础。服务起没起、数据库通不通、核心接口返不返 200，这些事不应该靠人打开浏览器点。

L1 用的是 Node 22 原生 fetch，零依赖，配一个 pymysql 做数据库断言。当时固化下来 24 条用例，16 条通过，8 条按设计跳过。

覆盖的东西很朴素：

  • 后端健康检查；
  • 管理端、商家端、会员端三个登录；
  • 门店列表、菜单列表；
  • 订单、优惠券这些核心表的落库口径；
  • 按天追新代码的用例，当天改了什么，就把可证伪的断言写进去。

跑不通的用例不静默跳过，而是带标签：blocked:oss 是上传链路被桶权限挡住，blocked:pay 是本地没有真实微信支付回调，blocked:wxtpl 是订阅消息模板不存在。跳过要写原因，不能假装它通过了。

L1 踩过的坑都写进了硬约束：所有业务接口一律 POST + JSON body；请求必须带 /siam-server 这个 context-path；地址必须写 localhost，不能写 127.0.0.1；登录后的令牌放在 Authorization 头里，不加 Bearer。

这些约束听起来琐碎，但每一条都是被坑出来的。比如 GET 请求带 query 参数，会被全局异常处理器吞成「系统异常，请稍后重试」，响应体里看不出真正原因，只能去翻后端日志。

L2：端到端，扫码之后收银台能看到订单

L1 证明接口活着，L2 证明这些接口连起来能完成一件事。

顾客端用 miniprogram-automator 驱动微信开发者工具，分两条流：

  • 浏览流 6 步：打开小程序、进首页、选门店、进点餐页、看商品、进详情；
  • 交易流 7 步：应用真实登录、自提点单、加购三件凑门槛、进结算页、关掉活动弹窗、提交 mockPay、去数据库核验订单落库。

交易流是最费劲的。它走的是应用真实 UI，登录要填手机号和验证码，结算页可能弹「加入会员」的活动浮层，商品还有起送门槛。自动化脚本要像人一样把这些都处理掉，不能在后端直接造一个订单假装成功。

这条流有一个副作用：每次跑都会创建真实订单。所以用例标了 mutating，默认关闭，跑完打印清理 SQL。测试可以写库，但不能装作没写。

商家端和收银台用 Playwright，首批固化了 4 步：登录、侧边栏渲染、页面无 5xx、收银台能打开。登录页是 hash 路由，按钮要用精确匹配，这些细节不写下来，下次还会踩。

还有一个很隐蔽的坑：会员登录是单点互踢的。自动化一登录，开发者工具里正在演示的会话就被踢掉。后来加了开关，会员用例默认跳过，要跑得显式打开，并且避开演示时段。

L3：人工验收，对着清单一条条过

前两层证明「系统能跑」，第三层回答「需求做到了没有」。

我按需求编号做了一张 46 行的验收表，每行对应一条需求，标注验证方式：走 L1 的哪个用例、L2 的哪条流，或者只能人工操作。09-24、09-25、09-26 各跑了一轮，记录自动生成到 docs/验收记录/。

这一层是最不体面的。46 行里有 34 行的需求描述还是「待同步」占位，验收口径也没定：是按需求书的 41 项，还是按追踪表的 46 行？口径没拍板，表就没法正式打勾。

所以那几天的验收记录看起来有点尴尬：L1 全绿、L4 达标，验收表里却大片空白。但这恰恰是真实状态——自动化测试做得再好，也不能替代「这条需求到底算不算做完」的判断。

我把这个缺口写进了上线保障清单：正式营业前必须先把口径定下来，补齐 34 行描述，再逐行打勾。没打勾之前，不能因为脚本全绿就说系统可以上线。

L4：并发，把平时撞不上的问题逼出来

第四层是并发。默认 50 并发，持续 15 秒，判定标准是失败率 0、p95 不超过 2 秒、p99 不超过 5 秒，压完健康检查还得是 UP。

读链路的表现不错。09-26 那轮压了 10421 个请求，全部成功，p95 94 毫秒。菜单和门店详情本来就是读多写少，这个结果不意外。

真正有意思的是登录场景。

第一次跑 50 并发登录，成功率 0%，压到后面健康检查都不可达了。降低到 5 并发、100 RPS 又完全正常。断崖式失败，说明不是代码慢，是某个资源被打满了。

顺着日志查下去，根因有四层：

  1. 管理端和商家端的 JWT 没有随机成分，同一个账号登录多次，token 字节级完全相同；
  2. 三张会话表只有主键索引，按 token 删除会话是全表扫描；
  3. createSession 由多条语句组成，并发下形成 InnoDB 死锁环，日志里出现 280 多次 Deadlock found；
  4. 登录请求持有 Controller 级事务，而登录日志用 REQUIRES_NEW 开了第二个数据库连接，连接池里的连接互相等。

HikariCP 默认只有 10 个连接，所以并发一过 10 就雪崩。表面看是「登录接口性能差」，实际是 token 设计、索引、事务、连接池四个问题叠在一起。

修复分几处：token 加随机成分；会话表补 idx_token 和账号唯一索引；createSession 改成单语句 upsert 加死锁重试；HikariCP 显式调到 20 个连接；登录日志去掉 REQUIRES_NEW。

改完再压，50 并发下 1283 个请求全部成功，121 RPS，p50 332 毫秒，p95 1258 毫秒，压完健康检查仍然是 UP。

这次 bug 改变了我对并发测试的看法。它不是为了证明系统快，是为了把平时撞不上的锁、索引、连接池问题在营业前逼出来。等到周五晚上客人排队时再发现，代价就不是改几行代码了。

本地环境得先能一键起来

测试写得再好，环境起不来就是摆设。所以配套做了一键启动。

start-all.sh 默认起三件套：后端 9411、管理端 5271、收银台 5270。MySQL 用单独的 start-mysql.sh。顾客端 H5 预览在 8010，小程序产物编译到 dist/build/mp-weixin，用开发者工具导入的是这个产物目录，不是仓库根目录。

端口这几个数字不是随便定的。后端原来用 9200，被本机一个无关进程占了，迁到 9411；管理端原来在 8001，后来让给别的服务，迁到 5271。这些变化都记在端口对照表里，不然过两周自己都忘了哪个是哪个。

工具链也有版本约束。管理端依赖 node-sass，只能用 Node 12；顾客端和收银台用 Node 20。两个版本都装在本机，启动脚本里分别指定，不靠全局 nvm use。

常驻用 launchd 管，关掉终端服务还在。日志统一放在 $RUN_DIR/logs/，出问题先看日志，不用猜。

扫码实验室：三个引擎同帧对比

收银台要支持扫码收款，得识别顾客的付款码。店里灯光暗、码可能小、可能倾斜，不能只靠「我手机上试了一下能扫」来判断。

我搭了一个小实验场：同一帧画面同时喂给三个引擎——浏览器原生 BarcodeDetector、项目现有的 @zxing/library 封装、ZXing-C++ 的 WASM 版本。另外生成几张测试码，分别做小尺寸、倾斜、低对比度。

实验场跑在本地 HTTPS 上，因为浏览器调摄像头要求安全上下文。它只解决「选哪个引擎」的问题，不替代真机扫码。真机的摄像头、对焦、光线，实验室模拟不了。

收个尾

四层测试跑下来，最大的收获不是「全绿」，是知道了哪里还没绿。

L1 和 L2 能证明系统不回退，L4 能证明读链路扛得住 50 并发。但它们证明不了支付回调幂等、退款金额正确、真实微信支付能通、后厨一定能出单。这些是营业级的问题，测试清单里单独列了 P0，还没做完。

脚本跑绿只是底线。真正敢开业，还得把那些「脚本测不到、但一定会发生」的事一条条补上。

部署和上线是另一段故事，下一篇单独写：湖里 Lakes：搬到微信云托管，部署和踩坑。
