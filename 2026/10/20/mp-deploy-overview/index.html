小程序从写完到能让人用，中间要过哪几道关

发表于2026-10-20|更新于2026-11-14|微信小程序部署
|总字数:1.7k|阅读时长:5分钟|浏览量:

做完两个小程序项目之后，我发现“写完”和“能让人用”之间隔着的不是一点代码，而是一串很容易被低估的事。第一个项目用云开发，第二个用云托管，两条路都走过一遍，这篇把部署这件事拆开讲清楚，给同样一个人做项目的人参考。

部署到底包含什么

代码在开发者工具里跑通，只是本地环境成立。要让别人也能用，至少要同时满足这些条件：

部分 要解决的问题
小程序包 体验版、审核、正式版，缺一个用户都打不开
后端服务 接口部署在公网，能稳定运行，挂了能重启
数据库 初始化、账号权限、备份，数据丢了没法补救
域名与备案 小程序请求域名、支付回调域名，国内服务器还要备案
HTTPS 小程序和支付都要求安全连接，证书过期会直接不可用
审核资料 主体、类目、隐私协议，填错会被驳回

任何一项没弄好，用户看到的就是“打不开”“加载失败”或者“系统异常”。而这些错误在本地都不会出现。

两条路：云开发和云托管

微信生态里常见的两种后端放法，差别不在语言，而在“谁管运行环境”。

云开发把后端拆成云函数、云数据库、云存储。不用买服务器，不用配 Nginx，不用管证书，登录态直接拿 openid。代价是数据库是文档型，复杂查询和事务不如关系型顺手，云函数也有超时和并发限制。

云托管是把一个容器跑在微信的机房。后端可以是 Spring Boot、Node、Go，只要能打成镜像；数据库可以用云托管 MySQL；域名默认带 HTTPS。代价是容器、镜像、端口、环境变量这些都要自己配，发版也多了一套版本概念。

一个省事但边界清楚，一个灵活但活多。选哪个，取决于后端要干什么。

任务派发走云开发

第一个项目是视觉中心的任务派发小程序，2026 年 7 月开始写，8 月底定稿。功能不复杂：发任务、认领、改状态、验收。用户都是微信里的人，不需要 Web 管理端，也不需要对接支付。

这种场景云开发很合适。任务、用户、记录分别放在几个集合里，认领操作用云函数做条件更新，避免两个人同时点到同一条。交付的图片直接进云存储。前端只负责展示和调用，没有一行服务器配置。

发布流程也短：开发者工具上传体验版，找几个同学真机点一遍，没问题就提交审核，审核过了点发布。整个过程没有碰过服务器，也没有备案和证书的烦恼。真正花时间的是权限规则、订阅消息和定时触发器这些细节，属于另一类坑。

湖里 Lakes 走云托管

第二个项目是精酿餐吧的点餐系统，情况不一样。店里有 PC/Pad 上的商家端和收银台，后端是改过的 Spring Boot，数据库是 MySQL，还要接微信支付。云开发的文档数据库和云函数不太适合承载这套东西，改成云托管更顺。

多出来的工作基本都集中在四块：

  • 容器：后端写 Dockerfile，前端三个静态包用一个 Nginx 容器托管；
  • 配置：数据库密码、对象存储密钥、支付商户号全部放环境变量，不能进镜像；
  • 支付：回调地址必须公网 HTTPS，验签失败要能查到是哪一步；
  • 域名：默认域名能直接用，绑自己的域名就要备案。

这些细节我单独写了一篇：湖里 Lakes：搬到微信云托管，部署和踩坑。这篇只留结论，不重复过程。

我现在的部署清单

两个项目走完，我把每次上线前要确认的事固定成一份清单。项目不同，顺序可能变，但项基本都在。

  1. 小程序主体、类目、隐私协议填好，需要备案的先把资料交上去；
  2. 域名实名和 ICP 备案提前做，别等发版前一天；
  3. 确认 HTTPS 证书有效期，默认域名也要看一眼；
  4. 数据库建好、账号给最小权限、确认备份策略；
  5. 后端环境变量逐项核对，密钥不进代码和镜像；
  6. 微信支付商户号、回调地址、验签配置对齐；
  7. 小程序后台的 request 合法域名、业务域名配好；
  8. 上传体验版，真机走一遍核心流程，再提交审核；
  9. 记下当前线上版本号和回滚方式，发版后做一次接口探针。

第 9 条看起来最像形式主义，但真出问题时最救命。知道上一版是哪个版本号，回滚就是一条命令；不知道，就只能一边猜一边改。

两条路的对比

把两个项目的部署路径画在一起，大概是这样：

    flowchart TD
  A[小程序前端] --> B{后端放在哪}
  B -->|云开发| C[云函数 + 云数据库 + 云存储]
  B -->|云托管| D[容器里的 Spring Boot]
  C --> E[上传体验版]
  D --> F[构建镜像并发布版本]
  D --> G[域名 + HTTPS + 备案]
  E --> H[提交微信审核]
  F --> H
  G --> H
  H --> I[用户能用]

云开发那条线短，是因为很多事平台替你做了；云托管那条线多出来的分支，就是自己要负责的部分。没有哪条更好，只有哪条更适合当前项目。

给后来人的建议

如果让我重新选一次，我会先问自己一个问题：这个项目到底需不需要自己写后端。

只需要在微信里用、数据关系不复杂、没有 Web 管理端和支付，云开发基本够用，省下来的时间可以拿去做功能。反过来，如果已经有 Spring Boot 或 Node 后端，或者店里有 PC 端、收银台、要接支付，那就别硬塞进云函数，直接用云托管或服务器。

还有两件事越早做越好：一是备案和审核的时间要留够，二是发版脚本和回滚方案要在第一次上线前就准备好。一个人做项目，最怕的不是写不出代码，而是上线当天发现某个证还没下来，或者新版本有问题却不知道怎么退回去。
